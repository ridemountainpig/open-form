A theme is a visual identity for forms: **tokens** (colors, fonts, radius,
spacing), optional **CSS** and **components**, and a `THEME.md` that tells
people and agents when to use it.

**Themes are references, and each form owns its look.** As in open-slide, the
themes in your project's `themes/` folder are what you and your agent read when
making a form. No form imports one or copies it whole: a new form starts from a
theme's tokens, and the rest of its look is written for it in its own `theme/`
folder, with only the parts that form uses.

```text
themes/
└── brand/                # a reference for new forms
    ├── index.tsx         # defineTheme({ colors, font, …, components })
    ├── brand.css         # optional, scoped to [data-of-theme="brand"]
    └── THEME.md          # palette, tokens, components, signature ideas, copy tone, do / don't
forms/
└── meetup/
    ├── index.tsx         # import theme from './theme/index.ts'
    └── theme/            # the form's own look: only this form uses it
        ├── index.ts      # its tokens (index.tsx once it has components)
        └── theme.css     # the CSS it needs, scoped to [data-of-theme="meetup"]
```

Every form made with [`open-form create`](/docs/cli/create) has a
`theme/index.ts`. Empty, `defineTheme({})` is the plain base look, which the
`classic` starter spells out token by token. A form without a `theme/` folder at
all gets the same look.

## Starting a form from a theme

```npm
npx open-form create meetup --theme terminal
```

`--theme` takes the theme from `themes/` when the project has one with that id,
and otherwise the starter of that name. It writes the theme's **tokens** into
the new form's `theme/index.ts`: colors and the dark palette, fonts, radius,
width, spacing, color scheme. Web fonts those tokens name come along into
`theme/fonts/`. The theme's CSS and components stay with the reference.

```ts title="forms/meetup/theme/index.ts"
import { defineTheme } from '@open-form-build/core';

export default defineTheme({
  font: 'ui-monospace, "SF Mono", …, monospace',
  radius: '4px',
  colorScheme: 'dark',
  colors: {
    primary: '#5af78e',
    // …
  },
});
```

The form imports it above its own stylesheet, so the form's CSS wins over the
theme's:

```tsx title="forms/meetup/index.tsx"
import { defineForm, Form } from '@open-form-build/core';
import theme from './theme/index.ts';
import './meetup.css';

export const config = defineForm({ title: 'Developer Meetup' });

export default function Meetup() {
  return <Form theme={theme}>…</Form>;
}
```

The form's root carries `data-of-theme="<form-id>"`, so the form's theme CSS
applies to this form only. The theme's `components` replace the defaults, and
[`<Form components>`](/docs/components/layouts#override-order) wins over the
theme's.

## Writing the rest of the look

Your agent writes the rest of the form's look in its `theme/` folder, reading
the reference's `THEME.md` and its code, and taking only what the form renders.
It works in this order, moving on only when the step before can't give the
look:

1. **Tokens** in `theme/index.ts`, including a built-in layout:
   `components: { Layout: SplitLayout }`.
2. **CSS on the runtime's own markup**, scoped to `[data-of-theme="<form-id>"]`:
   label and help treatment, pill or list-row choices, button glyphs and
   keycaps drawn with `::before` and `::after`, radios restyled as ticks. See
   [Theme CSS](/docs/reference/define-theme#theme-css) for the classes.
3. **Components** only for markup or behavior CSS can't give: a window frame,
   a wrapper an input needs for its underline or its `❯` prompt, keyboard
   shortcuts, auto-advance.

So a form in the `terminal` look carries the window, the ASCII progress bar and
the `❯` input lines as components, and draws its `? ` prompts, `( )` marks and
`register ↵` button in CSS. A field type it doesn't use, such as a `Select`,
isn't in its theme at all (`open-form check` warns when one is), and the
starters' later improvements never have to be copied into it.

## Changing a form's look

Edit `forms/<id>/theme/` by hand or ask your agent: tokens, CSS, components,
fonts. Only that form changes. In Studio, the form's preview has an
[**Adjust**](#adjust-a-forms-look) mode for its colors, fonts and shape.
Editing or deleting a theme in `themes/` never changes a form.

- **Renaming a form folder** changes its id, so update the
  `[data-of-theme="…"]` selectors in its theme CSS to match.
- **A form stands on its own.** `open-form check` warns when a form imports from
  `themes/` or from another form's folder.
- **Component classes are global.** Classes a form took from a reference, such
  as the terminal starter's `.tm-*`, aren't scoped to the form. If you embed
  several forms on one page and two of them style the same class differently,
  rename the prefix in one of them.

## References and starters

`themes/` holds the references your agent reads when it creates a form: the
project's brand theme, a starter you've adapted, a look made with
[`/create-theme`](/docs/skills/create-theme). A new workspace starts with an
empty `themes/`, and nothing renders from it in production.

Open Form ships five starters. Start a form from one, or add one to `themes/`
to adapt it first, the same way shadcn/ui components work.

| Starter | Feel | Layout | Good for |
| --- | --- | --- | --- |
| `classic` | Clean neutral card, every token spelled out | card | Product forms, internal requests, a safe default |
| `editorial` | Serif magazine, underline inputs, ink panel | `SplitLayout` | Agencies, B2B sales, applications, premium brands |
| `terminal` | Monospace CLI session, green on black, `? prompts` | terminal window | Developer events, devtools, hackathons, beta access |
| `brutalist` | Loud yellow, thick borders, hard shadows | card | Launches, waitlists, campaigns |
| `conversational` | One question per screen, rounded, soft violet, letter keys | `FocusLayout` | Surveys, NPS, quizzes, onboarding, RSVPs |

```npm
npx open-form theme list                      # the project's themes, then the starters
npx open-form theme add editorial --as brand  # → themes/brand/, a reference to adapt
npx open-form create meetup --theme brand     # a new form from brand's tokens
```

`theme add --as` renames the starter's copy: the `data-of-theme` selectors in its
CSS and the title in its `THEME.md` follow the new id, and `--force` replaces a
theme that already has that id. Changing a reference affects only forms you
start from it later.

## Tokens and components

**Tokens** recolor and reshape: `colors` and a `dark` palette, `font`,
`headingFont`, `radius`, `buttonRadius`, `spacing`, `width`, `layout`,
`colorScheme`. They cover most brand themes; pill buttons are just
`buttonRadius: '999px'`.

**Components** change how the form *feels*. Built-in fields only provide
behavior, and their markup comes from replaceable components (`Field`,
`TextInput`, `Select`, `ChoiceGroup`, …) and chrome (`Layout`, `Header`,
`Progress`, `Nav`, `Success`, `Notice`, …). Replace any subset and the rest keep
the default look. Validation, focus and the server's view of your fields don't
depend on them.

See [`defineTheme`](/docs/reference/define-theme) for every token and
[Layouts](/docs/components/layouts) for the built-in layouts and chrome.

## THEME.md

Each reference has a `THEME.md` with its mood, what it suits and when to avoid
it, its palette and every token, typography, layout and components (which parts
are CSS and which need a component), signature ideas (a few form-specific
elements that fit the theme, such as terminal's command that fills in as people
answer), copy tone, and do / don't. The
[`create-form`](/docs/skills/create-form) skill reads these to propose visual
directions and to write a form's look, and Studio renders it on the theme's
page.

## In Studio

`/studio/themes` is a gallery of the project's references: a live thumbnail of a
sample form in each theme, its name and one-line description, and a badge on
themes without a `THEME.md`. **New theme** adds a starter to `themes/` in one
click, or turns a description into a prompt to copy to your agent.

A theme's page shows a large preview of the sample form next to its `THEME.md`
and a spec drawn from its tokens: palette, contrast report, type samples and
shape. Switch the color scheme and the device, and jump to any page or the done
screen. The **Use it in a form** card shows the `open-form create <form> --theme`
command and a prompt to copy to your agent for a new form in this theme.

**Adjust** opens a drawer. **Quick tweaks** cover the primary and background
colors, body and heading fonts, radius and color scheme, with a contrast check.
**All tokens** has every color in the light and dark palettes, dark mode, fonts,
radius, button radius, width, spacing and frame. **Save to source** writes the
tokens straight into the file the reference lives in (`index.ts`, `index.tsx`
or a single-file `themes/<id>.ts`), so only forms started from it later get the
change. For anything bigger, describe the change and copy the prompt to your
agent.

### Adjust a form's look

A form's **Preview** tab has an **Adjust** mode next to Preview and Edit. It
opens the same panel on the form's own `theme/index.ts`: change colors, fonts and
shape and the preview beside it follows before you save, showing the palette
you're editing. **Save to source** writes the tokens into the form's theme file,
and fonts added from Google Fonts go into its `theme/fonts/`. A form without a
`theme/` folder gets a **Create look file** button, which writes
`theme/index.ts` and passes it to the form's `<Form>`. A `<Form>` that already
gets another theme (`theme={brand}`) is left alone: move what that theme sets
into the form's own `theme/` first. A look file the form doesn't import is
reported by `open-form check`.

<Callout type="info">
  The Themes pages and **Adjust** are available under `open-form dev` only. Keep
  tokens as plain literals inside `defineTheme()` so Studio can edit them; a value
  computed from a variable is left for you to change by hand.
</Callout>

## Web fonts

In **Adjust**, the body and heading font menus have **Add from Google Fonts…**.
Search by name, filter by category (including Chinese, Japanese and Korean), and
preview your own text. Picking a family downloads it into the theme and selects
it. `open-form theme font` does the same from the command line, for a reference
or, with `--form`, for a form's own look:

```npm
npx open-form theme font brand Inter          # → themes/brand/fonts/
npx open-form theme font meetup Inter --form  # → forms/meetup/theme/fonts/
```

```text
forms/meetup/theme/
├── index.ts               # import './fonts/inter.css'
└── fonts/
    ├── inter.css          # @font-face rules
    └── inter/             # woff2 files, split by character range
```

The form serves these files itself, so respondents never contact Google.
Linking `fonts.googleapis.com` instead would send every respondent's IP address
to Google. For a font that isn't on Google Fonts, copy its `.woff2` files into
`fonts/` and declare `@font-face` in the theme's CSS.

## Check contrast

```npm
npx open-form theme check brand          # a reference in themes/
npx open-form theme check meetup --form  # a form's own look
```

`theme check` reports WCAG contrast for every color pair forms actually use, in
light and dark, and exits non-zero when one fails. It reads hex, `rgb()`, `hsl()`,
`oklch()` and `oklab()`. Values it can't resolve, such as `var()` and
`color-mix()`, show as `?` and count as failures. Fix a failure by adjusting the
token: keep the hue, change the lightness.

## Create your own

Ask your agent to run [`/create-theme`](/docs/skills/create-theme). It reads your
repo's design system (Tailwind, CSS variables, shadcn, fonts), screenshots or a
description, starts from the closest starter, writes tokens, CSS, components and
`THEME.md` into `themes/<id>/`, and keeps `theme check` passing. New forms then
start from it with `create --theme`.

```text
/create-theme make it look like our product
```
